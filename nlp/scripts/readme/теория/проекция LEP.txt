пусть есть 3 модели:
source - базовая модель обученная задаче LM (предсказания следующего токена)
target - базовая модель (source) адаптированная для выполнения инструкций 
donor - адаптированная из какой-то базовой модели (например на другой язык или домен)

Пример:
source модель: Qwen/Qwen2.5-3B
target модель: Qwen/Qwen2.5-3B-Instruct
donor модель:  RefalMachine/ruadapt_qwen2.5_3B_ext_cl100k_bpe_32000_full_lr5e4_2k_bs256

Вопрос:
можно ли имея только эти 3 модели получить адаптированную базовую модель (как donor) которая еще и умеет (в какой-то степени) выполнять инструкции?
Никаких данных для обучения нет.

Решение которое приходит на ум:
Найти смещение source -> target и применить его к donor.
При этом смещение лучше применять только к эмбеддингам donor, а остальные слои взять из target (объяснение в Реализации)
Такой метод называется LEP (learned embedding adaptation)


ИДЕЯ:
смещение которое будем находить - матрица проекции из матрицы входных эмбеддингов source модели в матрицу входных эмбеддингов target модели,
аналогично находим матрицу проекции для выходных эмбеддингов (на самом деле находится матрица проекции эмбеддингов именно токенов donor-модели, см. Замечания). 
Далее просто умножаем матрицу эмбеддингов (входных/выходных) donor модели на найденную матрицу проекции
Матрицу эмбеддингов target модели заменяем на новую полученную проецированием матрицу эмбеддингов.
Так получим модель в которой все не эмбеддинговые слои (FF, линейные слои qkvo) адаптированы под выполнение инструкции, а слой эмбеддинга содержит как адаптацию donor-модели 
(например на другой язык или домен) так как мы проецировали эмбеддинг donor-модели, так и адаптацию под выполнение инструкций так как мы применили проекцию.

Замечания:
- проекцию нужно находить не из эмбеддингов source в эмбеддинги target, а из эмбеддингов токенов donor-модели полученных из эмбеддингов source в эмбеддинги
  токенов donor-модели полученных из эмбеддингов target. Так как проецировать будем как раз эмбеддинги donor-модели у которой могут быть свои токены.
- проблемы:
  1. donor-адаптация в полученной LEP-модели будет менее выраженной, так как она будет содержаться только в эмбеддингах (но вроде как считается что контекстное
      представление токенов при моделировании языка (в чем и заключается donor адаптация) как раз содержится в основном в эмбеддингах).
  2. в LEP-модели будет разрыв между эмбеддингами и остальными слоями, поскольку эмбеддинги будут соответствовать donor-модели (языку, домену),  
     а остальные слои привыкли обрабатывать именно эмбеддинги source-модели (другого языка, домена).
  Данные проблемы нельзя устранить такой же проекцией для не-эмбеддинг слоев, то есть найти проекцию например qkvo слоев source->target и применить ее к qkvo слоям donor,
  тк мы найдем проекцию из слоев qkvo которые обучались принимая на вход эмбеддинги именно source-модели и такая проекция не будет согласована с эмбеддингами donor-модели
  то есть применении такой проекции мало что даст, и при этом мы не можем применить такой же трюк как с эмбеддингами где мы на самом деле находили проекцию эмбеддингов 
  именно токенов donor-модели (что по сути является эвристикой, так как это не эмбеддинги donor-модели а эмбеддинги ТОКЕНОВ donor-модели полученные из эмбеддингов source/target-модели), 
  то есть мы не можем посчитать то какими бы были веса qkvo у source и target если бы они на самом деле принимали эмбеддинги токенов donor-модели, у нас просто нет способа как 
  это можно сделать, в случае эмбеддингов такой способ был естественным.
  Также нельзя например сделать проекцию для qkvo-слоев source->donor и применить ее к qkvo-слоям target. Так как это будет проекция из адаптации source в target
  которая тоже ничего не даст.
  Поэтому LEP можно применять когда source примерно совпадает с donor в плане задач к которым они адаптированы.
  То есть если например есть цепочки моделей:
	D1
  D2 -> I2 -> A2
	D1, D2 - domain, I2 - instruct, A2 - abliterate
  то нет возможности применить abliterate к D1, так как A2 это адаптация из instruct, а не domain и она будет мешать при просто применении проекции D1A2
  


ПРИМЕЧАНИЯ:

Новый токенизатор - токенизатор donor-модели в который добавлены из токенизатора target модели:
	- все добавленные и специальные добавленные токены которые отсутствуют в donor
	- шаблон чата и все специальные токены
	- если retain_nonalnum равен True то все токены в которых нет букв a-z (?)

- если эмбеддинги в target модели связаны то достаточно найти только одну проекцию (например только для входных эмбеддингов)
- необходимо найти проекцию эмбеддингов именно токенов donor-модели, но словарный запас donor модели может отличаться от source или target модели 
  (то есть для каких-то токенов может не быть эмбеддингов в source-модели), поэтому мы токенизируем все токены словарного запаса donor-модели токенизатором target-модели.
  При этом при токенизации токена может получиться несколько токенов - в этом случае применяется выбранная стратегия аггрегирования (например считается средний эмбеддинг
  всех эмбеддингов полученных токенов).
  Применяем найденную проекцию (умножаем на нее) к матрице эмбеддингов donor-модели. 
  Добавляем к полученной матрице эмбеддингов: 
    1. эмбеддинги всех добавленных и специальных добавленных токенов target-модели которые отсутствуют в donor-модели (так как могут быть специальные и добавленные токены
	    которые как раз используются для инструкций и содержатся в новом токенизаторе)
  	2. если retain_nonalnum равен True то все токены в которых нет букв a-z (?)
  При этом для всех добавленных и специальных токенов которые токенизатором target модели токенизируются в 1 токен берем эмбеддинг из слоя эмбеддингов target 
  а не полученной матрицы эмбеддингов (после проекции), тк в них они являются более выразительными для выполнения инструкций (фактически это будут специальные токены 
  которые есть в donor-модели (так как тех что не было уже были добавлены (см. 1)), для тех специальных токенов которые токенизируются в 
  2 и большее количество токенов аггрегированное представление в target эмбеддингах уже не будет таким выразительным, поэтому для них оставляем спроецированные)
  

Возможные разные режимы проекций:
   - описанная выше (проекция для токенов donor-токенизатора)
   - проекции считаются только для токенов target-модели, donor-токенизатор не используется 
   - идентичная проекция (так получим target-модель где эмбеддинги просто взяты из donor)
   - проекция токенов токенизатора target-модели строковые представления которых совпадают со строковыми представлениями токенов токенизатора donor-модели
     (в каком-то смысле промежуточный вариант между первыми двумя, то есть находим проекцию для токенов target-модели но только для тех что есть в donor-модели)

Возможные разные режимы аггрегирования токенов:
   - 'mean': среднее всех эмбеддингов
   - 'sum':  сумма
   - 'occ':  задается маппингом токен -> подтокены и их веса (вероятности)
	     если токен есть в мапе то находим взвешенную сумму всех эмбеддингов по вероятностям их подтокенов
	     если токена нет в мапе то также как mean

РЕАЛИЗАЦИЯ:

у source, target, donor модели должны быть одновременно входные и выходные эмбеддинги связаны или нет


применяем заданный режим проекции (conversion) к входному и выходному эмбеддингу (или только входному если эмбеддинги связаны в target модели):

	находим проекцию (матрицу hidden x hidden) заданным режимом проекции из слоя эмбеддингов source-модели в слой эмбеддингов target-модели токенов токенизатора donor-модели: 
	(токенизатор target модели используется для токенизации токенов токенизатора donor-модели для определения их эмбеддингов с помощью режима аггрегирования) 

	создаем новую матрицу эмбеддингов:
	- новый инициализированный слой эмбеддингов размера словаря нового токенизатора на размер hidden слоя эмбеддинга 
	  target модели, с тем же dtype и device (make_new_emb_matrix) и все эмбеддинги для токенов словаря donor токенизатора - это применение найденной проекции 
	  к текущему слою эмбеддингов donor модели (через @)
	- для всех добавленных и специальных токенов (get_added_vocab) нового токенизатора которые токенизатором target модели токенизируются в 1 токен
	  оставляем эмбеддинг из слоя эмбеддингов target 

	матрицу эмбеддингов target модели заменяем на новую матрицу эмбеддингов

	если в target модели входной и выходной эмбеддинги были связаны (target_model.config.tie_word_embeddings) то связываем их



режимы проекций:

PROJECTION_MODES = {
    "straight": make_straight_sub_proj,
    "union": make_union_proj,
    "conversion": mean_conv,
    "bypass":instant_conv,
    "sum_conversion": sum_conv,
    "occ_conversion": occ_conv,
}


mean_conv:
	make_conversion_proj:
	режим аггрегирования ='mean'

sum_conv
	make_conversion_proj:
	режим аггрегирования ='sum'

instant_conv:
	make_conversion_proj:
	новый токенизатор == старый токенизатор
	режим аггрегирования ='mean'

make_union_proj:
	находим проекцию из матрицы эмбеддингов source модели в матрицу эмбеддингов target модели токенов старого токенизатора строковые представления 
	которых совпадают со строковыми представлениями токенов нового токенизатора (get_union_tokens)

make_straight_sub_proj:
	матрица идентичности (I) размера hidden

occ_conv:
	загружаем маппинг токенов в их подтокенов с весами
	нормализуем веса (по L1-норме) чтобы получить вероятности
	режим аггрегирования ='occ'
